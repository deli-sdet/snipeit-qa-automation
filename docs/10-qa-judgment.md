# Part 6 — QA Judgment

## Release decision: intermittent failure to save some asset assignments, smoke suite green

I would recommend **not releasing** until the issue is understood, or releasing only with the explicit, documented risk acceptance of the product owner. A passing smoke suite shows that the main paths work in the cases it covers; it does not show that this defect is absent, because the smoke suite clearly doesn't reproduce it. Asset assignment is core data in an asset-management system: a lost assignment means the inventory is wrong, devices can't be traced, and audits fail. An intermittent failure is also hard for users to notice, so it can corrupt data quietly for a long time. I would quickly gather the failure rate, affected conditions (asset type, status, concurrency, user role) and whether the user sees an error or a false success. A false success makes it more severe. If the cause is found and fixed, I'd add a targeted regression test (repeated checkout plus a read-back via API) before sign-off. If the business must ship, I'd ask for a workaround, monitoring on assignment saves, and a fast-follow fix, with the decision recorded.

## Time pressure: two hours before a customer demo

First, I'd run the critical paths the demo will actually show: login, open the asset list, create an asset, find it, edit it, check it out and in. That means the `@smoke` suite plus the E2E lifecycle test, which take minutes. Next come a quick API smoke (read, auth, create/update) and the cross-layer check that an edit really persists after reload, because a demo that "saves" but loses data is the worst outcome. Then I'd do a short manual exploratory pass on exactly the demo script, data and browser, including the demo account's permissions. I would skip broad regression, cross-browser runs and edge-case boundaries. I'd tell the team clearly that those areas were not re-tested in this window, which known issues exist (e.g. the intermittent assignment save), and how to avoid them during the demo (use prepared data, avoid the risky flow, have a fallback). I'd also freeze changes to the demo environment after the checks pass.

## Flaky automation: passes locally, fails intermittently in CI

I'd start from the evidence rather than adding retries: CI traces, screenshots, videos and logs of the failed attempts, and the history of which test, step and error, and how often. Then I'd look for what differs between local and CI: parallel workers and shared data, slower CPU and network, headless mode and viewport, time zone and locale, environment variables, test order, and the state of the shared environment. I'd try to reproduce by running the test repeatedly in the CI image (`--repeat-each`, same worker count, `--workers=1` vs. many) to see whether it is timing, ordering or data related. Typical test causes are fixed sleeps, missing waits on network/AJAX, non-unique data or dependence on other tests. I'd fix those with web-first assertions, waiting on the actual response, and isolated data. To avoid masking real product failures, a retried pass is reported as **flaky** and gets a ticket, not counted as green. A quarantine is time-boxed with an owner. If the failure also appears for a real user flow (e.g. a save intermittently not persisting), it's raised as a product bug, not "fixed" in the test.
